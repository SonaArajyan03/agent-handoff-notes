Notes on handing work to coding agents
Working notes, updated as I learn things the hard way.

Agent capacity is a scheduling problem, not a budget problem

Every seat-based plan quietly creates stranded capacity. The fix is routing, not a bigger plan.

Agent subscriptions are sold per person, but the work does not arrive per person. On any given week a couple of people on a team burn through their limit by Wednesday while several others barely touch theirs. Add up the unused share and it is usually a large fraction of what the team is paying for.

The instinct is to buy more seats for the heavy users. That treats it as a budget problem. It is not: the capacity already exists inside the team, it is just parked next to the wrong person.

Why it strands

Three things have to line up for someone's spare capacity to be usable by someone else:

  • The blocked person has to know that spare capacity exists. Usually nobody can see anyone else's usage.
  • The task has to be portable — written well enough that a different person's agent can run it without the original author sitting there. That is a spec-writing problem.
  • Running it must not require sharing a login. This is where most informal arrangements die, and rightly so.

That third point is the one people underrate. “Just use my account” is how teams end up with a shared credential in a chat thread, no attribution on the work, and a plan-terms violation. The correct shape is to move the task to another person's own subscription, not to move the account to another person. There is a longer argument for that framing in this piece on using the AI capacity a company already pays for.

What to measure instead of seats

If you want a number that actually tells you something, stop counting seats and start counting these:

  • Blocked-hours. Time where someone had a ready, specified task and no capacity to run it. This is the real cost, and it is invisible on any billing page.
  • Handoff rate. How many tasks in a week were run by someone other than their author. If it is zero, your tasks are not portable and the capacity cannot move even in principle.
  • Spec rejection rate. How often a handed-over task comes back needing clarification. Rising rejection means you are shipping vagueness, not work.

The uncomfortable part

Routing spare capacity only pays off if tasks are written well, and writing tasks well is slower than doing the work yourself for anything small. So this does not help with small things, and pretending otherwise wastes everyone's afternoon. It helps with the medium-sized, well-understood, tedious work — which, fortunately, is most of the backlog.
