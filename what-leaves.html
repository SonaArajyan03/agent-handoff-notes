Notes on handing work to coding agents
Working notes, updated as I learn things the hard way.

What actually leaves your machine

People worry about their source code and then paste an API key into a task description. The risk is usually not where the worry is.

When a tool sits between your team and a coding agent, it is worth being concrete about what it receives, because the categories have very different consequences and they get discussed as one undifferentiated fear.

Four categories, in increasing order of how much I care

  • Task text. What you wrote in the brief. Almost always the largest volume and the least sensitive — until someone pastes a credential or a customer's data into it, which happens more than anyone admits. This is a training problem, not a vendor problem.
  • Repository metadata. Names, paths, branch names. Low sensitivity individually, but collectively it maps your architecture and your roadmap. Worth knowing it is retained; rarely worth blocking over.
  • Source code itself. The one everyone asks about first. The question that matters is not whether the agent sees it — it must, to work — but whether the routing layer in the middle also stores it, and for how long.
  • Credentials. The only category where a mistake is unrecoverable. If any component holds a token that can act as a person, that component is now part of your attack surface permanently, and no retention policy fixes a leak after the fact.

The question that separates designs

Ask where the agent authenticates. If the runner uses their own account and the middle layer never possesses a provider key, the fourth category is empty by construction — not by policy, by design. That distinction is worth more than any number of assurances about encryption at rest, because it removes the failure mode instead of mitigating it.

The same logic applies to whatever context capability the agent gets. A read-only, scope-limited, expiring credential that dies when the task ends is a fundamentally different object from a long-lived token with write access, even though both are "an API key" in a diagram.

What to do about the first category

Since task text is where real secrets actually end up, put a secret scan in front of it. A regex sweep for your own credential prefixes, run before a task is published, catches the realistic version of this problem. It is unglamorous and it will find something within a month.
